# Brief: run 2026-10-05-1510, family bias (blocked before running)

**What was tested and why.** This is the first test of the README's part 2: can the map's
bias be fitted to a task family? The plan was to fit `op_weights` on some members of two
families of threshold tasks on length-4 lists (sum>k and max>k). Each fit would then be
compared with uniform and with the other family's fit on held-out members, using
P(exact) from random sampling, with CI gates. No evolution yet. This was the third version of
the proposal, after two critiques.

**What happened.**
- The researcher built it: `family_bias.py`, plus a Rust sampler for the TAG alphabet
  (commit `3803bca`, branch `research/2026-10-05-1510`). The reviewer found the code correct
  after one repair.
- It was **not run**, because the task set could not pass its own calibration gate. In the
  reviewer's uniform probes (95M tapes), sum>10, sum>15, max>7 and most holdouts had **0
  hits**. Running it would have spent a budget slot to print that. **No budget used.**
- Rule of thumb from the probes: thresholds that are a built-in constant (1, 2, 5) come up
  about once per **1M** tapes (sum>5: 75 in 60M; max>1/2/5: 47/42/30). One ADD away is about
  once per **30–100M**. Anything further, never in 95M.
- In the reviewer's emulation of the fit (descriptive only), the matched fits raised P(exact)
  ≈ 7–8×, but the *mismatched* fits did too, ≈ 3–5×.

**What we learned.** On this alphabet, sampling only reaches simple tasks whose numbers are
already in the alphabet. That matters for any task-family design here. The emulation hints
that most of a fitted bias's gain is generic (aggregators, comparisons, constants), not
family-specific. That is a prior, not a result.
