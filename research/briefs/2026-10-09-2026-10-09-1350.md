# Brief: run 2026-10-09-1350. Can fragments come from programs that have not solved yet? (root 10, question 33) — not with this extractor: E/W_E 0.98×

**What was tested and why.** Fragments taken from exact solvers (F) beat library-free C-chain
blocks (W) on then-addition, 1.20×. But building them needs an exact-solver corpus that costs
about 48 000 worker-seconds. So the question was whether a cheaper source works. We ran the same
extractor on parents archived *before* their search first solved (run 1831's archive, about a
tenth of the cost), giving library E. E was scored against C-chain blocks with E's own length law
(W_E), with C held fixed. 1036's F/W/C runs on the same seeds served as paired references.

**What happened.** The run is complete and valid: 8 192 searches in 84 min. All libraries filled
32/32, and the 48 historical replays were bit-exact. 95% intervals over 16 corpora:
- **E/W_E 0.981× [0.911, 1.057]**, 7/16 corpora above 1. The same under every sensitivity.
- **E/F 0.843× [0.795, 0.892]**, 0/16 corpora above 1.
- E/W 1.007×.
- E/C 1.235×, which is just the block operator's gain (W/C was 1.227×).
- Solves: E 90.1%, W_E 90.2%.

Pre-registered rule 3 fired: *no worthwhile increment, end this source*. I expected rule 3 or
"unresolved", with E/F around 0.85–0.95. Both point estimates came in slightly lower.

**What we learned.** Pre-solve parents, run through this extractor, give a full library that is
no better than library-free chain blocks; gains above about 1.06× are excluded. It is clearly
worse than the exact-solver library. One visible difference: no pre-solve library contains the
`gt` comparison token, while every exact library carries `input first gt`. That makes "the
comparison joins carry F's gain" a natural hypothesis, but this run did not test it.
