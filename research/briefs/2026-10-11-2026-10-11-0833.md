# Brief: run 2026-10-11-0833 — does the tree-library recipe work when it learns from different sources?

**What was tested and why.** All 24 useful subtree libraries so far came from the same four double-gate (DG)
source cells, which are unusually repetitive. This run re-ran the same extractor on the four branch-sum (TS)
source cells instead (`A>B ? C+D : E+F`), giving 24 new builds. Each library was used as half the mutation
donors in restarted tree GP. It was scored on gate-sum B/C (12 cells × 24 builds × 6 repeats) against plain
R-tree, the saved DG libraries and size-matched random donors. It was also scored separately on the 8 native TS
targets. This was a portability test of a known idea (run-transferable libraries). Commit `28db964`, 9,216
scoring jobs.

**What happened.**
- Primary, B/C: R-TS ÷ R-tree **0.38 [0.34, 0.43]**, which passes the pre-set portable rule (upper < 0.80).
  There was no solve loss (1,728 vs 1,723 of 1,728), and the saving held in every build and every cell.
- The saving is not a donor-size effect: R-TS ÷ size-matched random 0.41 [0.34, 0.48].
- TS versus DG libraries: 1.03 [0.86, 1.22], unresolved.
- Acquisition from TS costs 0.25 M evaluations against DG's 2.9 M, and repays after **about 6** B/C searches
  (DG: about 64).
- Native TS: both libraries made search **more** expensive. TS-built libraries cost 1.78× [1.58, 2.00] and
  DG-built 1.33× [1.12, 1.57]. Plain tree GP already solves these on the first attempt 99% of the time.
- Audit: TS libraries are tiny 3-node sums with no comparison predicate (DG: 21/24 have one).
- The run took 53 min of scoring against a 150 min timeout.

**What we learned.** The library recipe is not tied to the DG sources: on B/C, learning from a different and
much cheaper source family gave about the same saving. That saving did not need DG's comparison predicate. The
same libraries hurt easy targets, so "always mix in the library" is not a safe default.
